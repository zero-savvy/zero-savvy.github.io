    🔐 Technical Overview¶

    This document describes the cryptographic mechanisms, protocol messages, and smart contract logic that make Redaplica a sound, complete, and trustless zero-knowledge game — without relying on any centralized server.

    ✅ Security Goals¶

    Redaplica is designed to ensure the following properties:

    • Soundness: A player cannot fake a higher score than they deserve. Furthermore, the challenge creator cannot cheat or reveal a final solution other than the original NFT.
    • Completeness: A player who correctly reconstructs the image can prove it and their proof is successfully verifiable by all parties.
    • Zero-Knowledge: No player reveals their guess during any phase of the competition.
    • Non-Interactivity: All game logic is driven by public commitments and a final reveal. Hence, there are no interactions required between any player and the challenger.
    • Serverless Verifiability: The entire process can be verified on-chain without any centralized trusted third party.

    🧩 Entities & Roles¶

    • Creator – Publishes a redacted image challenge and commits to the original.
    • Player – Submits a guess (privately) and later proves their score using ZK.
    • Smart Contract – Verifies commitment openings and submitted proofs. Keeps record of the scores and finally, distributes rewards.

    🔐 Cryptographic Primitives¶

    Component Scheme/Algorithm Purpose
    Hash Function Poseidon / Keccak Efficient commitments in SNARKs & Cairo
    ZK Proof System Groth16 Efficient proofs of score correctness
    ZK Verifier Garaga in Cairo On-chain Groth16 verification
    Score Function Hamming Distance Compares RGB differences over redacted pixels

    🔄 Protocol Flow¶

    1. Challenge Creation¶

    Step Actor Message/Event
    1 Creator Uploads image locally in browser
    2 Creator Selects redacted blocks (e.g., 10×10 chunks)
    3 Creator Computes C_img = Poseidon(Poseidon(original_image_bytes)\|\| r), where r acts as a random blinding factor.
    4 Creator Calls contract.commit(C_img, redaction_spec)
    5 Contract Stores hash commitment + metadata
    6 Creator Publishes redacted version (zeroed blocks) to IPFS or a file server

    ➡️ No image is ever uploaded to a server. Commitment is purely on-chain.

    2. Player Guessing¶

    Step Actor Message/Event
    1 Player Views redacted image
    2 Player Reconstructs redacted regions (via UI)
    3 Player Computes C_guess = Poseidon(Poseidon(guessed_pixels)\|\| r), where r acts as a random blinding factor. `
    4 Player Calls contract.submitGuess(challenge_id, C_guess)

    ➡️ Guess remains private. Only the hash is stored on-chain.

    3. Reveal Phase¶

    Step Actor Message/Event
    1 Creator Publishes full NFT version to IPFS or a file server
    2 Creator Calls contract.reveal(challenge_id, NFT_data, r)
    3 Contract Verifies NFT_data against the commitment C_image
    4 Contract Stores the H_redact corresponding to challenge_id

    ➡️ This is the only time the original image is revealed.

    4. Score Proof Submission¶

    Step Actor Message/Event
    1 Player Locally computes score = Hamming(guess, original)
    2 Player Generates Groth16 proof π_score stating that: my_score is Hamming(guess,orig) and I know r such that C_guess = Poseidon (Poseidon (guessed_pixels) \|\| r)
    3 Player Calls contract.submitProof(challenge_id, π_score, my_score)
    4 Contract Verifies proof using Garaga verifier contract against player's previously submitted commitment C_guess
    5 Contract Stores the my_score corresponding to challenge_id and the player ID

    ➡️ Contract only accepts scores backed by a valid ZK proof.

    5. Resolution & Reward¶

    Step Contract Action
    1 Contract Tracks highest valid score
    2 DAO/Contract After timeout, DAO calls contract.award(challenge_id, original_image_hash) function that mints NFT of original image to winner

    🧠 Why It’s Trustless & Secure¶

    Property Mechanism
    No Server Trust All hashing, guessing, proof generation happens locally in browser
    No Guess Leakage Only commitments (C_guess) are published until proofs
    No Score Forgery ZK proof binds player to original guess and correct score
    No Creator Cheating Commitment to C_img ensures they can’t change original after seeing guesses
    Verifiability All checks (hash equality, proof verification) are enforced in the smart contract

    📜 Smart Contract Responsibilities¶

    • Store commitments (C_img, C_guess)
    • Validate revealed images against commitments
    • Verify Groth16 proofs using Garaga
    • Track highest valid score
    • Mint NFT of the final revealed image to the winning address
